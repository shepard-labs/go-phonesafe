# Contributing to go-phonesafe

Thanks for contributing! This document covers how to report issues and submit changes.

## Reporting Metadata Issues

Phone number metadata (valid ranges, formatting rules, geocoding, timezones) is sourced from upstream [google/libphonenumber](https://github.com/google/libphonenumber). We cannot accept direct edits to generated files. Instead:

1. File an issue here describing the problem
2. If it affects the upstream library, also file it at [Google's Issue Tracker](https://issuetracker.google.com/issues/new?component=192347)
3. Once the upstream library is updated, regenerate with `make generate LIBPHONENUMBER_PATH=../libphonenumber`

For the issue, include:

```markdown
* Country:
* Example number(s) and/or range(s):
* Number type ("fixed-line", "mobile", "short code", etc.):
* For short codes, cost and dialing restrictions:
* Where or whom did you get the number(s) from:
* Authoritative evidence (e.g. national numbering plan, operator announcement):
```

## Reporting Code Bugs

When filing a code issue, include:

- Go version and OS
- A minimal reproducer (input string, region, expected vs actual behavior)
- If possible, what the upstream Java/C++ library returns for the same input

## Submitting Changes

### What we accept

- Bug fixes
- New tests for untested behavior
- Performance improvements (with benchmarks)
- Documentation and hygiene cleanups
- New APIs that match the upstream `libphonenumber` signature

### What we don't accept

- Changes to generated files (`*_gen.go`) — these are overwritten by `phonesafe-gen`
- New features not present in upstream libphonenumber (unless discussed first)
- Changes to the metadata model or generated data structure without updating `cmd/phonesafe-gen`

### Process

1. **Open an issue first** for non-trivial changes — saves everyone time.
2. **Fork and branch** from `main`.
3. **Write tests first** for bug fixes. The test should fail before the fix.
4. **Keep changes minimal** — don't refactor adjacent code unless it directly relates.
5. **Run the full suite:**
   ```bash
   go test -race ./...
   go vet ./...
   ```
6. **Include upstream evidence** — if the fix is based on upstream behavior, reference the upstream source file/function in a comment.
7. **Port tests from upstream** when adding new functionality. Copy the comment with the upstream test method name for traceability.

### Tracing to upstream

go-phonesafe ports behavior from upstream libphonenumber. When implementing or fixing something, cite the source:

```go
// Ported from: java/libphonenumber/src/com/google/i18n/phonenumbers/PhoneNumberUtil.java
// Method: isValidNumber(PhoneNumber)
```

This is especially important for edge-case behavior where the "right" answer is defined by upstream, not by intuition.

## Code Generation

The metadata is generated by `cmd/phonesafe-gen`. If you change the data model in `internal/metadata/` or `internal/data/`, you must also update the generator:

```bash
# Develop locally against your libphonenumber checkout
make generate LIBPHONENUMBER_PATH=../libphonenumber

# Validate source metadata parsing without writing files
go run ./cmd/phonesafe-gen \
    -input ../libphonenumber/resources \
    -validate-only
```

Generated files are deterministic — running the generator twice with the same inputs must produce byte-identical output. Use the `make generate` command above to regenerate.

## Testing

Quick reference for running tests:

```bash
# Run all tests
go test ./...

# Run with race detector
go test -race ./...

# Run upstream test vector coverage
go test -cover -coverprofile=coverage.out ./...
```

- All new behavior requires a test.
- Bug fixes must include a regression test in `regression_test.go`.
- When porting upstream tests, include a comment referencing the upstream test method.

## Performance

Benchmarks are tracked in the README. If you introduce a regression >10%, add a note in the PR. Target benchmarks:

| Operation | Target |
|-----------|--------|
| Parse | < 5 µs/op |
| IsPossibleNumber | < 100 ns/op |
| IsValidNumber | < 2 µs/op |
| Format (E.164) | < 3 µs/op |

## Style

- Match the surrounding code style — don't reformat unrelated parts.
- No comments for obvious code — let well-named identifiers do the work.
- Keep functions focused — if a function needs a paragraph to explain, split it.
- Error messages are user-facing: be specific ("missing country code for +1-650") not generic ("invalid number").
